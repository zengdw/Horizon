### [Nginx HTTP/2 flaws enable unauthenticated remote code execution](https://www.wiz.io/blog/nginx-http2-rce-vulnerabilities) ⭐️ 8.0/10

Two Nginx HTTP/2 vulnerabilities, tracked as CVE-2026-123633 and CVE-2026-123007, reportedly allow unauthenticated remote code execution against servers that have HTTP/2 enabled. The stated mitigation is to disable HTTP/2, and the reporting material describes practical constraints on exploitation rather than a confirmed, weaponized exploit. The source content supplied here is limited to the two CVE record links, so the technical details of the flaws and their exact severity are not independently established in this item.

hackernews · speedping · Nov 18, 15:19 · [Discussion](https://news.ycombinator.com/item?id=50547374)

**「Context」** HTTP/2 is an optional protocol layer in Nginx that is not enabled by default, so exposure depends on whether a given deployment has turned it on. A remote code execution flaw in protocol handling is significant because it can be triggered by an unauthenticated network request without prior access to the server.

**「What to do」** Operators should check whether HTTP/2 is enabled and apply the vendor fix or disable HTTP/2 as the interim mitigation, since the workaround is a configuration change rather than a code patch. Teams relying on the open source repository should also verify they are running a build that includes the fix, given community reports that the change landed in the repository before the public advisory.

**「Community discussion」** Commenters dispute the practical severity: one argues the bug was fixed in the open source repository about a week earlier and that a simple public service announcement to disable HTTP/2 should have followed, while another claims exploitation needs roughly 128 GB of HTTP/2 traffic plus specific CPU instructions and calls it a non-issue. Others note HTTP/2 is not enabled by default and is used by only about 12% of servers, which they describe as still large at Internet scale. These are opinions and unverified claims, not established facts.

The hardened configuration is aligned with DISA Security Technical Implementation Guide \(STIG\) benchmarks, so a secure baseline is the starting state rather than a post-install hardening project. This applies only to Server Core installs; Windows Server Desktop Experience installs do not include the changed stance. The release is a public preview, and the compatibility tradeoffs implied by the hardened defaults are not detailed in the source.

rss · Ars Technica · Nov 18, 20:41

**「How STIG hardening worked before」** DISA&\#x27;s Security Technical Implementation Guide \(STIG\) is a standard framework that gives system administrators recommended hardening guidance to follow, but it has historically been something admins applied manually after deployment. In prior Windows Server releases, administrators started from a blank canvas and had to implement hardening configurations themselves, with secure baselines available but not enabled by default. The hardened-by-default state applies only to Server Core installs, not the Windows Server Desktop Experience option.

**「Compatibility concern」** Because the hardened-by-default state is limited to Server Core, organizations relying on Desktop Experience installs will not receive it, and teams adopting Server Core should expect the stricter default configuration to affect compatibility with workloads and tools that assume a standard, unhardened baseline.

hackernews · runesoerensen · Nov 18, 23:52 · [Discussion](https://news.ycombinator.com/item?id=50554038)

**「Why case conversion can corrupt memory」** Ruby implements String and Regexp case conversion \(upcase/downcase\) in C, operating directly on the underlying byte buffer. **「What developers should do」** Since these are memory corruption bugs in core language features rather than optional extensions, any Ruby application that upcases or downcases strings — especially with non-ASCII encodings — should update to the patched release named in the advisory rather than treating the issue as limited to unsafe or third-party code.

**「Technical analysis in the comments」** tptacek argued that the Windows-1252 case-conversion code checks buffer headroom one character at a time and therefore overruns when a trailing ß expands to SS, while pentestercrab posted a concrete Shift\_JIS reproduction that produced an oversized result on an unfixed build.
