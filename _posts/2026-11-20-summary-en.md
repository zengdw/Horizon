### [PostgreSQL 19 Released With WAIT FOR LSN Standby Consistency](https://simonwillison.net/2026/Nov/19/postgresql-19/) ⭐️ 8.0/10

PostgreSQL 19 has been released, shipping roughly two months later than the usual September cadence because the team had to address a wave of AI-reported vulnerabilities. Its headline feature is a new \`WAIT FOR LSN\` command that gives applications sending reads to standby replicas &quot;read-your-writes&quot; consistency: a session can wait until the standby has replayed the write-ahead log up to a specific log sequence number \(LSN\) before running a query, so it can read data it just wrote on the primary. The pattern works by capturing the current LSN after a write \(for example via \`pg\_current\_wal\_insert\_lsn\(\)\`, returning a value like \`0/0306EE20\`\), storing it, and then issuing \`WAIT FOR LSN &\#x27;0/0306EE20&\#x27; WITH \(TIMEOUT &\#x27;0.1s&\#x27;\)\` on a later request; the timeout is optional and produces an error if the replica does not catch up in time.

rss · Simon Willison · Nov 19, 20:43

**「Release cadence and the AI-driven delay」** PostgreSQL traditionally ships its annual major feature release in September, with each new major version adding capabilities that require upgrading from the prior version. This year&\#x27;s cycle was disrupted when AI/LLM-driven bug reporting generated a volume of reported vulnerabilities that the PostgreSQL Global Development Group could not clear in time, pushing PostgreSQL 19 from a planned late September or early October release to late November 2026.

**「What this changes for read-replica applications」** Applications that route reads to standby replicas can now implement read-your-writes consistency natively instead of hand-rolling replication-lag workarounds: after a write, the app captures the current LSN \(e.g. via pg\_current\_wal\_insert\_lsn\(\)\) and issues WAIT FOR LSN on the standby before reading, so a user sees their own just-committed change. This replaces custom patterns such as MediaWiki&\#x27;s binlog-position tracking built on MySQL&\#x27;s WAIT\_FOR\_EXECUTED\_GTID\_SET\(\). The trade-off is extra round-trips — capturing the LSN on the primary and explicitly waiting on the standby — so for many workloads reading from the primary remains simpler and faster, and the optional TIMEOUT clause returns an error if the replica does not catch up in time.

### [OpenSSL EVP\_EncodeBlock\(\) Buffer Overflow \(CVE-2026-121481\)](https://github.com/openssl/openssl/pull/33652) ⭐️ 7.0/10

A buffer overflow in OpenSSL&\#x27;s EVP\_EncodeBlock\(\), the base64 encoding function, has been reported as CVE-2026-121481 with a CVSS score of 9.8, and a fix is proposed in pull request 33652. According to community analysis, the function misbehaves when its input exceeds roughly 1.5GB, and the flaw is enabled by the API&\#x27;s design: the caller computes the required output length with a nontrivial formula and does not pass the output buffer size, so the implementation cannot validate it. The reported severity is disputed in the discussion, with commenters arguing that 9.8 is exaggerated because the function is internal and exploitability depends on whether untrusted data can reach it.

hackernews · JacobHenner · Nov 20, 02:01 · [Discussion](https://news.ycombinator.com/item?id=50569226)

**「Background」** EVP\_EncodeBlock\(\) is part of OpenSSL&\#x27;s EVP encoding API and produces base64 output, documented in the EVP\_EncodeInit/EVP\_EncodeBlock man pages. Unlike APIs that take an output buffer length, this interface relies on the caller to size the destination buffer correctly, which is why an oversized input can overflow without the library detecting it.

**「Impact」** Services that base64-encode untrusted data in a single call are exposed: a commenter notes that a base64 encoding service reading all input into memory at once and calling EVP\_EncodeBlock\(\) would be exploitable, while protocols that cap block size \(for example with a 16-bit length field\) would not reach the trigger. Developers should check whether untrusted input can reach this function with very large sizes and apply the fix in pull request 33652, while treating the 9.8 score as a vendor-reported figure rather than a confirmed worst-case risk.

**「Community Discussion」** Commenters disagree on severity: one argues CVSS 9.8 is exaggerated and far below Heartbleed because the function is internal and exploitability hinges on untrusted input reaching it, while another points out the underlying API design is flawed since the caller must compute buffer length and cannot supply the output size for validation. A separate thread of comments expresses vulnerability fatigue and skepticism toward the &quot;never reinvent the wheel&quot; approach, which are opinions rather than technical findings.

### [Java JDK base64 &\#x27;java4shell&\#x27; crash taken over by Oracle](https://github.com/openjdk/jdk/pull/32781) ⭐️ 7.0/10

A crash in the Java JDK&\#x27;s base64 implementation, described as a SIGSEGV that can be escalated into remote code execution and nicknamed &quot;java4shell,&quot; was reported to Oracle and the fix was taken over by Oracle rather than merged from the community pull request \(openjdk/jdk PR 32781\). According to community comments, the underlying SIGSEGV was first reported in June 2026 and isolated to base64 in September, with Oracle asking the PR author on October 1 not to proceed until approval and taking the work over by October 28. The Hacker News thread also debated whether LLM-assisted researchers independently found the bug or recalled it from training data, but that remains speculation rather than an established finding.

hackernews · notmine1337 · Nov 19, 11:47 · [Discussion](https://news.ycombinator.com/item?id=50558906)

**「Why it matters」** A SIGSEGV is a segmentation fault — an invalid memory access that crashes the process — and in a language runtime like the JDK it can sometimes be turned into arbitrary code execution if an attacker controls the memory that gets dereferenced. Base64 decoding is a common, widely used utility in the JDK, so a flaw there can affect many applications that decode untrusted input.

**「What to do about it」** Because Oracle took over the fix, JDK versions still carrying the unfixed base64 flaw remain exposed until they apply Oracle&\#x27;s patch, so anyone decoding untrusted base64 input should treat the crash as a potential remote code execution vector rather than a benign denial of service and track Oracle&\#x27;s release for the update.
